# 04. 並行リクエストで起きる競合と対処

## なぜ並行実行が起きるか

- 複数の端末（別ターミナルの Claude Code、別マシン）が同時に繋ぐ
- 1つの Claude でも、モデルが複数ツールを**同時に**呼ぶことがある（ただし実測した1回の実行では逐次だった）
- 「状態を調べるツール」自身が負荷の原因になってはならない

## 起きる競合と起きない競合

全ツールが read-only で、サーバが持つ可変状態はキャッシュ（と統計）だけ。

| 競合の種類 | 本構成 | 対処 |
|---|---|---|
| 書き込み競合（ロストアップデート等） | **発生しない**。read-only に限定した設計上の帰結 | 不要 |
| 順序の競合（到着順で結果が変わる） | **発生しない**。2026-07-28 の Streamable HTTP はセッションレスで、サーバに端末ごとの状態がなく、1リクエスト=1 POST | 不要 |
| **共有状態の破壊** | `psutil.process_iter()` が返す `Process` は**モジュールグローバルにキャッシュされて使い回される**。`Process.cpu_percent()` の基準値はそのインスタンスに載るので、スレッド間で共有すると壊れうる | 呼び出しごとに新しい `Process` を作る（`process_snapshot`） |
| **B. 重複作業** | 20並列の `journal_recent` が `journalctl` を20回起動する | **TTL キャッシュ + single-flight** |
| **C. 資源競合** | 無制限の並行実行が観測対象のホスト自身を重くする | **セマフォ + 明示的なバックプレッシャ** |

### 訂正メモ: `psutil.cpu_percent()` は壊れない

設計時は「`psutil.cpu_percent()` はグローバルな前回値を持つので並行サンプリングで値が壊れる」と想定し、`threading.Lock` を入れる計画だった。**これは誤りだった**:

- psutil 7.2.2 は基準値を `threading.current_thread().ident`（スレッドごと）で保持し（`psutil/__init__.py` の `_last_cpu_times`）、blocking モードは `t1/t2` をローカル変数で持つ
- 実測: 32スレッドで同時に blocking サンプリング → 全て 9.9〜13.6%（0..100 に収まり、破綻なし）

よって CPU 用の Lock は入れていない。**本当の共有状態は `process_iter` のキャッシュ側**で、こちらはソースで機構を確認した（`_pmap`、`psutil/__init__.py`）が、破綻自体を再現したわけではない。

## 前提: ハンドラは `def`、`async def` にしない

SDK は同期 `def` のツールを `anyio.to_thread.run_sync` のワーカースレッドで実行する（`mcp/server/mcpserver/resolve.py`）。
スレッド上限は anyio の既定 **40**（実測で確認）。

| 書き方 | 結果 |
|---|---|
| `def` + blocking（`subprocess.run` / `cpu_percent(interval=1)`） | スレッドで実行され、**他のリクエストは止まらない**（← 本サーバ） |
| `async def` の中で blocking を呼ぶ | イベントループが止まり、**全クライアントが止まる** |

## 対処の仕組み（`ops/concurrency.py`）

### 1. TTL キャッシュ + single-flight（`Coalescer`）

TTL キャッシュだけでは、**期限切れの瞬間に N 本が一斉に実測へ走る**（cache stampede）。
single-flight は「同じキーの実行中は先頭の1本だけが計算し、後続は待って結果を共有」する。

| | 効くところ | 役割 |
|---|---|---|
| TTL キャッシュ | 時間方向 | 直近に計算した結果を再利用 |
| single-flight | 同時方向 | 実行中の同じ計測に相乗り |

- キーは `(ツール名, 引数…)`。`top_processes` は引数（並び順・件数）に依らず**全プロセスのスナップショット1つ**を共有し、切り出しは各呼び出しで行う
- 先行実行が `ToolError` で失敗したら待機側にも同じエラーが伝わり、**失敗はキャッシュしない**
- 想定外の例外は一般化して伝播し、詳細はログだけ
- キャッシュは最大256件（引数はクライアント由来なので無制限に増やさない）
- 返り値は共有される。呼び出し側は変更してはならない

| TTL | 対象 |
|---|---|
| 2秒 | `resource_usage` `top_processes` |
| 10秒 | `system_overview` `disk_usage` `listening_ports` `service_status` |
| 3秒 | `tail_log` `journal_recent` |

### 2. 外部コマンドの同時数制限（`command_slot`）

`systemctl` / `journalctl` は同時 **4本**まで。溢れたら最大3秒待ち、それでも取れなければ **待たせ続けず**
`サーバが混雑しています。少し待って再実行してください。` を返す。

> キューに無限に積むと、クライアントはタイムアウトするだけで**原因が分からない**。
> エラーとして返せば、モデルがそれを読んで自分で再試行できる（バックプレッシャを明示的に渡す）。

### 3. 入力のクランプ

`lines` ≤ 1000（journal は 500）、`limit` ≤ 50、`interval` ≤ 5.0。SDK が関数に入る前に弾くので、1回の呼び出しが占有できる時間とメモリに上限がかかる。

### 4. タイムアウト

外部コマンドは 5 秒（`journal_recent` は 15 秒）。超過は `ToolError`。

## 観測する: `server_stats`

サーバ自身のカウンタを返すツール。重複排除が**実際に効いたか**を、テストがログ解析なしで数えられる。

| キー | 意味 |
|---|---|
| `<tool>.computed` | 実測した回数（先頭の1本） |
| `<tool>.cache_hit` | TTL 内で再利用した回数 |
| `<tool>.coalesced` | 実行中の計測に相乗りした回数 |
| `command.launched` | 外部コマンドを起動した回数 |
| `command.busy_rejected` | 混雑で断った回数 |

1リクエストは必ず `computed` / `cache_hit` / `coalesced` のいずれか1つに数えられる（`load_test.py` の会計チェックはこれを使う）。

## 検証（`make load` — 22項目）

サーバは別プロセス。20クライアントを同時接続して確認する。

| # | 内容 | 実測結果 |
|---|---|---|
| S1 | `resource_usage`（1.4秒計測）を20並列 | 実測1回 + 相乗り19。**所要 1.48s**（20回分なら 28s）。全応答の CPU% が 0〜100 |
| S2 | 同一の `journal_recent` を20並列 | **`journalctl` の起動は 1 回**。20人が同一の結果を受け取った |
| S3 | 並び順・件数が違う `top_processes` を20並列 | スナップショットは1回。各応答が要求どおりの並びと件数 |
| S4 | 別々のユニット名の `service_status` を20並列 | 会計が合う（起動 + 拒否 + キャッシュ = 20）。ハング・想定外エラー無し。負荷後も健全 |
| S5 | 3秒かかる呼び出しの実行中に軽い呼び出し | 軽い方の最悪レイテンシ **0.03s**（遅い方は 3.00s）。スレッド実行が効いている |
| S6 | `command_slot`（プロセス内）: 上限4 + 溢れ6 | 通るのは4本だけ。溢れた6本は待たされず「混雑」で断られる |
| S7 | `Coalescer`（プロセス内）: 失敗経路 | 10並列で実行1回・失敗が全員に伝わる／失敗はキャッシュされない／想定外の例外の詳細はクライアントに漏れず**ログには残る** |

- **判別力の確認**: `Coalescer.call` を素通し（`return fn()`）に改変したサーバに同じテストを当てると **S1・S2・S3 が FAIL**（`journalctl` の起動が 1→20 回）。保護が無ければテストは落ちる。
  この確認で S3 のアサーションが弱い（カウンタが空でも通る）ことが見つかり、会計条件を足して直した。
- **S4 の限界**: この環境では `systemctl show` が速く、実サーバで自然に「混雑」は起きなかった。混雑拒否の経路は S6 でプリミティブ単体を決定的に検証している。
- 2回連続で実行して安定（TTL キャッシュが温まった経路も通る）。

```bash
make load                  # 20並列
uv run python scripts/load_test.py -n 40 --url http://127.0.0.1:8848/mcp    # 並列数を変える
```

## 既知の限界

- ロックもキャッシュも**プロセス内**。`uvicorn --workers N` にすると保護が worker ごとに分断される。本トライアルは1プロセス固定（`mcp.run()` は1プロセスしか起動しない）
- セマフォは**外部コマンドだけ**を絞る。`psutil` の全プロセス走査（`top_processes`）は TTL + single-flight でしか守っていない
- `disk_usage` が応答しないマウント（切れたネットワークFS等）に当たると、そのワーカースレッドは戻らない（タイムアウト無し）
- TTL の間は**古い値**を返す（最大 2〜10 秒）。厳密な即時性が要るなら `MCP_CACHE_TTL_SCALE=0`
- レート制限・認証は無い（`127.0.0.1` 待受が実質的な防御）
